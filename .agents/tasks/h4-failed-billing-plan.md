- B. Pending file_url download failure (engine.ts:260-282): usage 0. No charge. Unchanged.
- C. Step loop failure, `catch` at engine.ts:554-587: covers connector error, timeout, missing/DISABLED connection, parse/attachment errors, DB errors during the loop, AND errors thrown AFTER the SUCCEEDED transition (billing update, `job.updateProgress(100)`, `dispatchCoreWebhook`, because the success block is inside the same `try`). The catch builds `usage = summarizeOperationUsage(usageMeasurements)` and writes it onto the row (totalCostUsd, costMissing, hasUnpricedCost) but never charges. THIS is the one path to change.
  Important detail: `usageMeasurements` is pushed only AFTER `runExternalApiProcessor` returns (engine.ts:~470). Inside the processor usage is read after a successful HTTP response (external-api.ts:293-337); HTTP/timeout/SSRF/attachment errors throw before any usage is known. Therefore the known cost of a failed op = sum of steps that completed before the failing step (multi-step pipelines) plus, after a post-SUCCEEDED exception, the full cost. A single-step op that fails inside its own step has known cost 0 (we never fabricate an estimate for calls whose response we did not see). Say this plainly in the final report: for the common failed sub-op case (one connector call that errored) the new rule charges 0 because no usage was returned; money the provider billed without returning usage cannot be known.
- D. Post-success exception path (subset of C, the double-charge hazard): billing already done, then `updateProgress`/`dispatchCoreWebhook` throws, the catch overwrites state to FAILED and would charge the SAME usage again. Must be prevented in-process (see design).
- E. On a rerun: `resumeFromStep = row.currentStep` (engine.ts:~340), completed steps are restored from `stepsResultJson`, but `usageMeasurements` starts EMPTY, so the row's `totalCostUsd/usageBreakdown` are OVERWRITTEN (absolute SET) with only the new attempt's steps, not cumulative. Each attempt therefore measures only its own real spend (steps re-executed are real new spend), and the attempt's own billed delta is correct for that spend. Known pre-existing gap (do not fix): spend of steps completed by a crashed attempt is on neither the row nor totalUsed, because usage is not persisted per step. Document it, offer per-step usage persistence as an optional follow-up.
- F. Do NOT charge in these paths (would be 0 for leaves, and a double count for parents). Unchanged.
- G. `submit.ts:227` QUEUE_SUBMISSION_FAILED, `enqueueSubStep` WORKFLOW_TIMEOUT marking (workflow-engine.ts:343-352): no usage. Unchanged. A timed-out ACTIVE sub-op keeps running and bills itself on its own completion.

### 1.5 Known cost of a FAILED op (requirement b)
Use the in-memory `usage.totalCostUsd` computed by `summarizeOperationUsage(usageMeasurements)` in the catch, i.e. the same value already written to the row's `totalCostUsd` in that very FAILED transition. Do not re-read the row (for a leaf the row is still 0 before the transition; for a parent it is the children sum). `summarizeOperationUsage` already does the right thing: unpriced measurements (`costSource==='unpriced'`) add 0 and set `hasUnpricedCost`; null costs add 0 and set `costMissing`. So we only ever charge the KNOWN portion, never an estimate for unpriced/missing usage. The explicit record is the two flags already persisted on the row by the same transition, plus a new `logger.warn('[BILLING] ...')` naming operationId, charged amount and the flags when `costMissing || hasUnpricedCost` so finance can reconcile.

## 2. Design: one increment point, exactly once (requirement 2)

Rule: the cost incurred by an AI call is charged to the key once, by the operation that executed the call (the leaf run in `runPipeline`), whatever its final state (SUCCEEDED/FAILED). Parents (workflows) never charge for FAILED/CANCELLED/PAUSED because they own no AI spend. CANCELLED (previous task) stays: no parent charge, sub-ops bill themselves.

Implementation (single file, no third increment point, no schema change):
- In `runPipeline` (engine.ts), inside the function before the `try`, add `let billedCostUsd = 0;` and a local async closure `chargeIncurredCost(usage)`:
  - `const delta = usage.totalCostUsd - billedCostUsd;` return if `!operation.apiKeyId || !(delta > 0) || !Number.isFinite(delta)`.
  - `await db.update(apiKeys).set({ totalUsed: sql\`${apiKeys.totalUsed} + ${delta}\` }).where(eq(apiKeys.id, operation.apiKeyId));` then `billedCostUsd += delta;` (increment the tracker only after the UPDATE resolved, so a failed UPDATE is retried by the catch instead of being lost).
- SUCCEEDED block: replace the inline UPDATE (engine.ts:526-531) by `await chargeIncurredCost(usage);`. On the first call delta == usage.totalCostUsd and the SQL is identical, so SUCCEEDED behavior is unchanged (pinned by test C2).
- Catch block: after the FAILED `transitionOperationState` and BEFORE/AFTER `dispatchCoreWebhook`? Put the charge directly after the transition and before the webhook (same order as the success path), wrapped in its own `try/catch` that logs `logger.error('[BILLING] failed to charge ...', {operationId, amountUsd}, err)` and swallows: a billing DB blip must not throw (BullMQ would retry and re-run paid steps) and must not block the FAILED webhook. Add the `[BILLING]` warn for `costMissing || hasUnpricedCost`.
- Why this is exactly-once without a column: (1) repeated calls within one run (post-success exception, section 1.4 D) are made idempotent by `billedCostUsd` (second call has delta 0, SUCCEEDED-then-FAILED charges the amount once); (2) across BullMQ attempts each attempt only measures/charges steps it executed itself (resume skips completed steps), so no spend is charged twice and no new spend is skipped; (3) finish-function repetition: `failWorkflow`/`completeWorkflow`/`recordCancelledUsage` add nothing new for FAILED/CANCELLED. A new `operations` column/migration is NOT required, so no STOP/ask is needed (if during implementation a real need appears, STOP and `send_message` severity "warning" BEFORE creating any migration; the repo convention is numbered SQL in `drizzle/` plus `drizzle/meta`, latest is `0015_business_operation_persistence.sql`).
- Not done on purpose: atomically merging the charge into the transition transaction (requires changing the shared `transitionOperationState` API that many writers and the H4 guard use; not needed for correctness here). Note the pre-existing small window (crash between the state write and the charge loses that charge) as a limitation, identical to today's SUCCEEDED behavior.

Files touched by implementation: `lib/pipelines/engine.ts` (only `runPipeline`), new test files. NOT touched: workflow-engine.ts (except read-only), state-transition.ts, submit.ts, billing routes, schema/migrations, webhook code.

## 3. Scope: affected pipelines/workflows (requirement 3)
Billing is global per API key, so the rule applies to EVERY op executed by `runPipeline`: all standalone pipelines/endpoints (any `extract:*`, `analyze:*` etc. routed through `pipeline:<slug>`) and every workflow sub-step. Workflows in `WORKFLOW_REGISTRY` (workflow-engine.ts, 12): disbursement, lc-checker, payroll-verify, structure-compare, brd-analyze, payment-account-management, financial-report-translation, statement-analyze, tracing-portal, loan-appraisal, account-opening, margin-deposit. For these, a FAILED sub-op now charges its known cost; a FAILED parent charges nothing extra (no re-add). Expected consequence to state in the report: keys with a spendingLimit reach `totalUsed >= spendingLimit` (402 in submit.ts) sooner, because failed runs now count. `billing/usage` (SUCCEEDED-only report) will no longer sum to `totalUsed`; leave it unchanged (API contract) and mention it to the user as an open question.
